# TAG 关联卡片与 MDPro3 实现分析

## MDPro3 如何查找关联卡片

2026-09-19 核对上游提交 `228e4ae652d23cb0e6e466a35e2281ce9b1d630a`，提交时间为 2026-09-02。核对的是该提交的源码，并未接管或操作用户的 MDPro3 窗口。

1. **先查生成表。** [`RelatedCardsManager.Search`](https://code.moenext.com/sherry_chaos/MDPro3/-/blob/228e4ae652d23cb0e6e466a35e2281ce9b1d630a/Assets/Scripts/MDPro3/Duel/YGOSharp/RelatedCardsManager.cs) 首次使用时载入 `StreamingAssets/RelatedCards.json`。以卡号为键，将 `ID`、`Arch`、`Level/Link/Rank`、`Race`、`Type`、`Other`、`Targets` 七类数组合并；去掉自身、重复、未安装卡和衍生物。分类名用于存储，最终列表合并显示。
2. **生成表来自脚本和卡库。** [`build_related_cards.py`](https://code.moenext.com/sherry_chaos/MDPro3/-/blob/228e4ae652d23cb0e6e466a35e2281ce9b1d630a/Tools/RelatedCards/build_related_cards.py) 读取 CDB 字段、Lua 常量、筛选函数和部分召唤素材条件，也允许人工条件文件覆盖。它把能静态解析的条件与卡库比对，加入卡片自身的系列字段，生成反向关联；ID／系列的反向边仍归原类，其他反向边放入 `Targets`。部分过宽的自动筛选组会被舍弃。
3. **没有条目才使用文字后备。** [`CardsManager.RelatedSearch`](https://code.moenext.com/sherry_chaos/MDPro3/-/blob/228e4ae652d23cb0e6e466a35e2281ce9b1d630a/Assets/Scripts/MDPro3/Duel/YGOSharp/CardsManager.cs#L717) 取卡名、系列名与效果中括号内的文字，再扫描其他卡的名称、描述及系列字段。生成表已有该卡条目时，不与文字后备结果混合。

因此，它并非只比较卡名，也不是即时运行决斗来证明配合。脚本中「能影响此卡」「以此卡为素材」「排除某系列」等不同含义，都可能形成查找线索。不能把整张关联表直接当成系列成员表，尤其不能沿关联链无限扩张 TAG。

## 工具箱采用的方式

原有 TAG 已按 CDB 的 `setcode` 判断系列归属，并支持手动包含／排除；它的缺口是缺少发现支援卡的入口和依据。这次保留现有 TAG 编号、名称、别名、卡组注释与方案分类格式，在其上新增独立的本地关联索引。

| 依据 | 行为 |
| --- | --- |
| 卡库系列 | 按四段 16 位系列编号及子系列位匹配，不使用名称前缀；子系列可属于父系列，不与兄弟子系列混淆 |
| 效果提及系列 | 只识别括号／引号内、与卡库系列正名或无歧义别名完全对应的文本 |
| 效果点名卡片 | 只识别括号／引号内的完整卡名，并支持反向查询“哪些卡提及此卡” |
| 脚本引用 | 静态读取 `listed_names`、`listed_series`、部分 `IsCode`／`IsSetCard` 系列调用及 `AddCodeList` 等调用中的纯数字参数；忽略注释、字符串和无法解析的表达式 |
| 同名卡关系 | 使用卡库 `alias` 建立双向查看关系，不擅自认定为同一张卡的所有效果 |

索引独立实现，不复制 MDPro3 源码或分发其生成表；只读当前安装的 CDB、系列表和脚本，不联网、不执行 Lua。扩展与超先行脚本按现有资源覆盖顺序取用，卡库／系列资源重载后重建索引。异画的脚本选择沿用本程序现有解析规则。

只查当前成员或指定卡片的**一层直接关系**。系列 TAG 不会因为其中一张卡属于另一系列，就把那一整个系列合并。衍生物、已包含和已排除卡不重复显示为候选。宽泛的同种族／等级／属性关系不自动扩展，无法识别的动态 Lua 条件可能漏查；结果不是完整的配合推荐或规则合法性证明。

## 使用

1. 打开左侧 **TAG 管理**，选择一个系列；下方“TAG 关联候选”显示可能遗漏的支援卡及其依据。
2. 可按卡名／卡号和依据类型筛选。点击 **加入 TAG** 先加入当前草稿，点击顶部 **保存修改** 后参与共同匹配。
3. 成员卡、候选卡和搜索结果都提供 **关联卡片**。例如从“烙印融合”可以发现“阿不思的落胤”；再点“返回 TAG 关联”恢复当前 TAG 的范围。
4. 新建自定义 TAG 时，可先搜索一张种子卡并查看关联，不必先保存一个空标签。
5. “包含的卡牌”可区分卡库系列和手动加入；“已排除的卡牌”可恢复被移除的成员。未安装卡保留编号，不能假装其资源已恢复。

候选永远不会自动改写 TAG。确认加入的卡保存到既有 `include_cards`，影响卡组建议、自动方案分类和下一次智能识别；成员排除沿用 `exclude_cards`。已经保存的卡组主／副 TAG 和手动方案分类不会被追溯改写，步骤、起手与对局记录也不修改。只读查看不产生迁移文件；修改标签仍使用版本校验、原子写入和 `backups/tags/` 备份。

卡组浓度仍按主卡组＋额外卡组副本数统计；方案浓度仍只计实际参与路线的我方卡牌种类。各自阈值和主／副 TAG 规则保持现有行为，识别依据补充“卡库系列／手动加入”。

## 验证入口

- `npm test`：包括关联索引的合成边界用例，以及既有卡组、方案、模块化和智能识别回归。
- `npm run test:desktop -- --tags-only`：后台 Electron、真实本地卡库、隔离数据。检查白石与青眼、烙印融合与阿不思，覆盖发现、确认加入、保存失败恢复、跨页面草稿、排除恢复、重载持久化、过期请求、卡图悬停和窗口宽度。
- `npm run test:packaged -- --tags-only`：相同流程从打包程序启动；验收记录见 [1.37.0 验证记录](verification-1.37.0.md)。

这些检查验证关联发现与 TAG 数据流，不等于验证两张卡在任意实战局面中可以合法配合。其他决斗能力继续沿用 1.36.1 的范围。
