# 本局临时方案 · 1.17

## 操作流程

1. 在决斗页确认构筑与起手，点击「生成临时方案」。来源、偏好和精确匹配在同一页面调整。
2. 采用候选后进入步骤图。前进一步或点击相邻下一节点，表示当前操作已经照做。浏览旧节点不撤销确认；不能跳过未确认步骤。
3. 随机获得卡牌或随机堆墓后，选择实际卡牌，可重复添加。遇到阻抗，选择对应步骤，填写对方发动的手牌阻抗及实际支付的手牌费用。
4. 后台根据填报重放。确认的前缀保留，旧后续被替换，优先采用当前偏好排在首位的新后续。没有后续时保留已确认部分，显示待生成；可调整来源后重试。
5. 结束本局、改换起手或重新开始会释放该局后台推演。临时方案不自动成为正式方案，也不进入展开草稿列表；关闭应用后不恢复临时教程。

## 状态与边界

「已确认」指用户确认照做或填报了实际结果，软件没有识别外部对局。尚未完成的步骤与终场是推演。确认只推进独立的本局模型，不向真实展开提交输入，不伪造实战操作日志。

随机结果在用户填报前隐藏具体身份。填报仅调整一次性重放副本中现有牌组实例的顺序，并要求实际处理结果与所填卡牌的区域、份数一致；效果、费用、触发、通常召唤次数与限制仍由原规则核心处理。不能把库中不存在、剩余份数不足或当前步骤没有发生的抽牌／堆墓当成事实。

阻抗根据用户报告的卡片，在该步骤的重放副本中由规则核心处理，要求确实产生针对当前操作的无效或移除事件。当前入口支持手牌发动及可完成复核的选择；复杂目标、额外费用、盖放卡、持续限制等不能仅凭卡名完整表达时会拒绝近似续算并保留原进度。新的随机结果和额外对手响应仍需继续填报。来源不足和搜索达到预算不等同于规则上无解。

每项计算保留构筑、引擎、脚本和来源版本；改换来源或偏好后旧候选不能继续采用。低层选择归入对应的召唤／效果步骤，但原始决策顺序仍用于重放。此前已确认前缀可以回看；重算前缀之前的更早历史暂不提供再次改写入口。

## 实现与检查入口

`/api/modular/dispatch` 的 `duel` 调用方使用 `plan`、`plan-adopt`、`plan-confirm`、`plan-observe` 与 `plan-close`。后台实例带 `purpose=duel_planning`，原生窗口始终隐藏，不覆盖展开场地，不保存用户窗口设置。退出时回收自身进程；原始资源、卡组、正式方案与其他展开保留。

原生位置同步合并过期的等待请求，最多保留当前发送与最新等待布局，避免滚动后长时间重放旧坐标。独立模块化页面与展开继续使用原场地。

- `npm test`：基础逻辑、状态保护与布局请求合并。
- `npm run test:modular -- --suite=pipeline`：后台生成、页面不跳转、采用步骤图、确认与回看、无实战输入、错误填报保留原进度、结束释放。
- `npm run test:modular -- --suite=forecast`：原生录制抽牌／堆墓来源，用户填写具体结果后重新生成后续，以及报告灰流丽后改走通常召唤路线。
- 对应发布包使用 `npm run test:modular:packaged -- --suite=pipeline` 与 `--suite=forecast`。
- `npm run test:desktop` / `npm run test:packaged`：原有桌面流程回归。

验收实例使用隔离测试数据和内部接口，不使用全局鼠标或按键。测试数据、截图与成品包保留本地，不纳入 Git。
