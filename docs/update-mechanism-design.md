## 3. 版本模型与文件归属

分别保存三类版本，另用一个组合 ID 确定实际运行内容：

1. **工具箱版本**：应用版本、记录格式读写范围、资源管理器格式、原生适配接口版本。
2. **引擎构建 ID**：客户端和核心上游提交、本地补丁哈希、架构、构建参数／依赖、定制 EXE 哈希、消息协议和采集快照版本。核心目前包含在定制构建内，仍应单独记录其来源。
3. **卡牌资源 ID**：上游显示日期、发布条目／云文件 ID、包体 SHA-256、数据库／脚本／图片／配置的内容清单哈希。日期相同但内容变化是另一修订。
4. **运行组合 ID**：上面引擎与资源的精确匹配、加载优先级、配置默认值版本和适配范围。活动指针只指向这一个组合，不能分别更新“当前引擎”和“当前卡库”两个指针。

更新描述至少包含 `schemaVersion`、`releaseId`、`revision`、`sourceFolderId`、`sourceEntryId`、`providerFileId`、`archiveSha256`、`archiveSize`、`baseResourceIds`、`requiredFiles`、`replaceFiles`、`deleteFiles`、`targetTreeHash`、`engineBuildId`、`adapterAbi`、`protocolSchema`、`supportedToolboxRange`、验证用例版本和验证结果。字段是拟定契约，不是上游已提供的数据。

补丁依赖匹配“上游资源基线及所需文件指纹”；不能要求定制 EXE 与上游原版 EXE 相同。若未来包包含二进制差分，必须补充原版程序前置指纹和定制构建的转换策略，不能把差分施加在本地适配程序上。

建议新格式数据目录位于 `%LOCALAPPDATA%/YGOTrainer/managed-v1/`，其中：

```text
user/                    配置、牌组、方案、会话、原生 profile 和备份
generations/<bundleId>/  只读引擎、卡库、Lua、图片、版本配置和完整清单
state/                   active、previous、事务日志、锁和状态
downloads/               包体缓存、分块校验和及断点状态
staging/<transactionId>/ 独立解包、构建目标和隔离验收数据
catalog/                 来源快照、兼容描述和受信验证清单
```

保留现有 `_trainer` 内部的 YDK／JSONL／JSON 结构，只调整它所属的稳定用户根目录。`system.conf` 用户值留在 `user/`，上游默认配置在资源代内；新增配置项通过有版本、可恢复的迁移合并，不能覆盖用户选择，也不能因保留旧值而悄悄改变脚本加载优先级。必须影响规则的配置纳入组合验证。

旧 `runtime/` 不删除。第一次迁移前使用现有清点、独立备份、逐文件校验思路扩展到 profile 和配置，停止旧服务及训练，再复制至新格式目录并验证。个人文件不进入更新包、公开兼容清单或 Git。

**旧程序边界**：1.2.0 及以前不认识新选择器，无法要求它遵守未来组合契约。采用新目录格式后，旧版只访问保留的旧目录；旧目录是迁移时快照，不与新数据双向同步。升级顺序一致和共享新数据的保证，从首个支持本机制的工具箱版本开始。回退到 1.2.0 不等于把新记录写回旧目录。

## 4. 检查、识别、下载与手动导入

### 检查策略与界面

- 推荐默认启用自动检查；应用启动 30–60 秒后，距成功检查已满 24 小时才检查，应用运行期间约每 24 小时再检查一次。少量随机延迟避免集中请求，不阻塞启动。
- 自动下载、自动安装已验证组合设独立选项。首版默认检查并提示；开启自动安装后，在已验证范围内完成下载、准备、验证和空闲切换。允许一键关闭所有自动检查／下载／安装，保留手动检查和导入。
- 手动检查立即执行，但合并重复点击与并发请求。网络失败有限重试并退避，不能高频轮询。
- 展示当前工具箱、引擎构建、卡牌日期及修订、当前组合、可用／已下载／待生效版本、更新说明、说明来源和上次检查时间。
- 处理状态明确区分：无更新、发现更新、等待验证资料、下载中、需手动下载、缺少前置补丁、校验失败、不兼容、准备中、等待展开结束、切换中、已生效、已恢复。不能把检查失败显示成无更新。
- 无逐卡更新说明时明确显示“上游仅提供程序＋数据更新标题”；本地计算的文件变化另列，不能编造更新内容。

### 同日重发与依赖

先比较条目 ID、提供方文件 ID、名称、大小、时间、ETag 等，再用包体 SHA-256 和规范化内容树哈希确定身份。日期或文件名相同不能去重，链接变化但内容相同也不重复安装。

上游可能保持相同条目、文件名、大小及时间后替换内容。没有可靠源端哈希时，只看元数据无法保证发现这种情况：建议每 7 天在允许自动下载时重新获取当前最新包计算哈希；仅检查模式展示“内容校验距今多久”，手动提供强制内容核查。弱 ETag 不视为内容证明。

把更新建成依赖图，按前置资源 ID 排序，在独立候选目录依次应用每个必要补丁并验证中间和最终目标。已经满足目标内容则直接报告一致，不再次安装基线包。缺少必需前置包、依赖成环或前置指纹不符时，列明缺项，保留活动组合；不自动改用完整安装包，也不猜测仅补最后一包可行。

### 下载与导入

将“来源目录解析”“分流页解析”“蓝奏云会话／下载解析”“文件传输”做成可分别替换的模块，锁定目标目录和更新包路径。页面结构变更、Cookie 流程变化、验证码、失效或超时返回可解释状态，不持续尝试绕过人工验证。

下载至 `.partial`，检查实际文件类型、长度、包体哈希及存储空间。续传先重新解析过期直链，核对 ETag／长度／`Content-Range` 与已有分块；服务器返回 200 或身份变化时丢弃本次候选的无效分块并重新下载，不能拼接不同修订的内容。取消、失败均不触碰活动资源。

手动入口接收下载得到的更新 EXE 或已支持归档，只读取文件、不执行安装器。手动包与自动包共用分类、前置依赖、兼容、事务和恢复路径；手动导入不是跳过检查。无法确认身份的包可保留作待审核候选，不能直接激活。

## 5. “自动兼容”的可执行规则

兼容判断必须在获取说明、归档分类、资源准备和动态验收之后进行，并以完整组合为单位。

| 变化 | 可以自动处理的条件 | 必须暂停的情况 |
| --- | --- | --- |
| 已识别的图片／文本修订 | 来源和哈希已审核，依赖完整，已有引擎与脚本组合经验证；精确选择替换和删除文件 | 不明重命名、未知覆盖关系、规则所需文件缺失 |
| CDB 和 Lua 更新 | 数据库结构、加载次序、Lua 版本／接口及公共库要求符合已验证描述，受支持组合的验收通过 | 仅语法通过但组合未经验证；新核心 API、公共常量或处理语义无法确认 |
| 上游 EXE 改变 | 维护者已对相应源码重放／修改本地适配、构建并验证，发布匹配的定制引擎构建 | 只有上游可执行文件；内部字段、协议、嵌入、起手或记录适配冲突 |
| 扩展库／扩展脚本／归档 | 双方加载顺序、重名卡号和覆盖规则均经过核实并进入支持配置 | 当前 Python 明确拒绝的 `.zip`／`.ypk`，或新扩展模式、路径冲突 |
| Bot、安装器和不使用的附属内容 | 提取规则明确列为当前组合不需要的组件，并已验证不构成依赖 | 陌生 EXE、DLL、脚本安装动作或未分类文件，不能随意忽略 |

自动检查内容包括：路径越界、重解析点、Windows 保留路径／大小写冲突、非预期同名条目、资源数量及解压上限、数据库完整性／字段类型和卡号关联、脚本语法／公共库加载、已知 API 需求、图片解码、配置合法性、架构及目标文件哈希。正常怪兽、衍生物、别名和脚本复用必须按已验证规则处理，不能简单要求每个数据库 ID 都有同名 Lua。

静态 API 扫描不能证明 Lua 动态调用和未来卡效正确。最终还需要基于真实核心的用例：效果发动与费用、连锁／无效、选择与区域移动、额外召唤及素材、双方起手和 AI 响应，以及本次更新涉及的代表性卡牌。出现未知消息、采集缺口、Lua 错误、崩溃或错误终局，不能通过。

建议维护者保存一份“经验证组合清单”：源包哈希、依赖、受支持工具箱范围、定制引擎和目标资源树哈希、测试结果。首版可随工具箱携带；要使未来已验证资源无需重新发布整个工具箱即可自动安装，需要另行建立维护者可发布的签名清单地址。应用内固定验签公钥，拒绝无效签名及未经允许的清单降级，离线继续使用已安装组合。

这份清单用于证明“工具箱验证过这个匹配”，不冒充上游发行者签名。本次计算的 SHA-256 能标识内容和检测传输损坏，本身不能证明发布者身份。未验证的新包可以被自动发现和下载，不能自动升级成已验证状态。自动化测试降低维护工作，无法消除规则／接口变化后的开发适配。

## 6. 准备、切换、恢复和升级顺序

### 安装事务

```text
发现 → 确定依赖 → 下载与校验 → 分类提取 → 构造完整候选组合
     → 静态检查 → 隔离真实引擎验收 → 等待空闲
     → 持有独占锁并再次检查 → 提交活动组合 → 重建服务及缓存 → 生效确认
```

1. 从指定的完整基线构造候选代；补丁中的全量组件按其明确规则替换，增量组件按清单覆盖／删除。不能把包里没出现的文件一律删除或一律保留。
2. 所有用户数据都在代目录之外。第一版采用独立副本，暂不通过可写硬链接去重，以免修改候选影响旧代。
3. 在隔离用户目录中验证候选。测试只运行受信的定制引擎，不运行上游安装器，不把用户牌组／记录发送给外部服务。
4. 展开、原生编辑器或其他引擎使用资源时可以准备候选，但延后生效。统一数据根锁、引擎使用租约、真实进程身份和文件占用共同把关；切换前阻止新展开并再次核对，消除检查后又启动的竞态。不强行结束用户展开。
5. 停止旧服务中的 Catalog／图片缓存及资源读取者，确认原始记录落盘。在同一磁盘卷内提交单一活动记录，记录前代、候选、阶段、事务 ID，并作持久写入。只有已完成准备及验证的代可以被指向。
6. 重启后服务、原生端和前端都回报同一组合 ID；卡牌查询／图片缓存使用组合 ID。生效确认通过才清除待确认状态。
7. 进程崩溃或断电后根据日志、代清单与指针恢复到“旧代完整可用”或“新代完整可用”。切换后确认失败则恢复前代，保留失败候选和诊断信息；不能把半套文件当作可用状态。

设置“恢复上一个可用组合”入口；服务无法启动时，桌面壳的恢复入口仍可用。恢复同样要求空闲和兼容检查，只改变资源／程序组合，不回退个人记录。若前代不被当前工具箱支持，则提供对应可运行的工具箱版本或历史只读模式，不能盲目换回不兼容引擎。

保留活动代和至少一个已知可用前代；被正在运行的会话引用的代不得回收，用户锁定的复现代也保留。按当前约 1.28 GB 资源规模，两个保留代约 2.6 GB，另加候选、压缩包和备份；三个未压缩代约 3.8 GB。下载前按真实清单计算所需空间，空间不足先保留当前版本。

### 工具箱与资源更新的两种顺序

应用包内的 `runtime.zip` 改为“随包种子组合”。首次无数据时可选用；已有活动组合时仅注册候选，不自动向其复制文件。以后修复当前资源从其对应缓存／代清单恢复，不能从任意旧安装包填补单个文件。

工具箱程序也按版本目录并排保留，协调器记录最近可用的应用路径及组合。新版本先做资源和用户记录格式预检，通过后才允许激活及必要迁移；失败时可启动保留的旧程序。用户数据格式迁移必须备份、可续做，并核实旧程序的读取能力，不能依靠回退资源解决记录格式不兼容。当前 ZIP 交付若仍采用手动启动，新程序的预检失败页应明确给出保留的旧版入口；不能声称已经存在应用自动升级器。

| 顺序 | 规定行为 |
| --- | --- |
| 先资源，后工具箱 | 资源先切到 R1。新工具箱启动先读取活动组合；兼容则继续使用 R1，不因包内 R0 更旧而覆盖。若需要新定制引擎，必须找到已验证的“新工具箱＋新引擎＋R1”整体组合后切换 |
| 先工具箱，后资源 | 新工具箱先验证并保留可接受的现有组合，再按相同兼容描述安装 R1。资源下载／准备不依赖当时应用包内资源的日期 |
| 两项共同要求升级 | 允许提前下载准备；当前工具箱不支持的资源不激活。确认新工具箱和完整候选都齐备后联合切换，不产生新库＋旧脚本的过渡状态 |
| 没有兼容组合 | 保持原来可工作的工具箱和组合，提示所需软件版本／适配。新工具箱必须先做兼容预检，不能以静默降级资源解决启动问题 |

对同一目标工具箱和同一目标资源，两个顺序最终必须得到相同组合 ID、资源文件树、有效配置迁移结果和用户数据，而不只是日期文字相同。并发检查、导入、工具箱升级和恢复均由同一个协调器串行提交。

## 7. 用户数据与历史记录

- 配置、牌组、前置设计、正式方案、草稿、历史、删除恢复副本和迁移备份不属于版本资源。更新／恢复前后校验数量及内容指纹，不能为使新资源通过验证自动改写牌组卡号或删除旧卡。
- 每次新会话冻结工具箱、引擎、资源、组合、记录协议及报告格式版本；继续保留实际双方牌组、起手、顺序、随机状态、规则设置和卡牌全文。
- 补充首次出现的衍生物、由效果产生或引用的非起始牌组卡牌文本，来源必须是该会话固定的资源代。读取旧历史不能查询今天的卡库来冒充当时文本。
- 对旧记录中不存在的脚本版本等字段标为未知，只有可核实来源才补充旁路信息，不伪造历史。保留原始 JSONL、会话元数据、旧报告；新投影另存文件，并按日志协议选择解码器。
- “重新展开同一次尝试”要求完整原组合可用并匹配；仅 EXE 相同不够。旧组合已回收时可以阅读冻结报告，精确重试需先恢复对应受支持组合。
- “以此条件新建展开”可使用当前受支持组合，但必须显示规则／资源版本变化，产生新 UUID 和新版本记录，保留原方案不变。
- 恢复资源后仍保留使用新资源生成的方案和记录。若旧资源不含某牌组的卡，阻止相应新展开并说明，不能删除该牌组或改写已有报告。

## 8. 验收矩阵

以下均是实施后的要求；除第 10 节所列检查外，本次未执行这些新机制验收。

| 场景 | 必须达到的结果 |
| --- | --- |
| 无更新／当前基线一致 | 显示无更新或内容已一致，活动 ID、资源、用户数据不变；不因没有安装收据重复安装 0901 包 |
| 正常更新 | 来源、依赖、静态检查及真实效果用例通过后整体切换；查询新／改卡文本与图片及实际结算均符合候选 |
| 重复检查／重复导入 | 合并任务，相同包只提交一次；重启后依然不会重复安装 |
| 同日重发 | 同日期、同名、甚至同大小但不同 SHA-256 被识别为新修订；先重新验证，不覆盖已知可用修订 |
| 增量依赖缺失／错误基线 | 明确缺少哪个前置包或文件指纹；不安装、不跳补丁、不下载完整包 |
| 下载失败／人工验证／页面变更 | 当前版本可继续使用；合理退避，明确手动下载及导入入口；检查失败不伪装成无更新 |
| 续传 | 支持 206 的服务器正确续传；200、过期直链、ETag／长度变化均不拼接错包；最终完整哈希一致 |
| 损坏包／错误格式／同名架构 | 截断、哈希错误、解压异常、路径越界和非预期重复条目在候选阶段失败；已识别多架构包只选择正确分支 |
| 不兼容包 | 未知 API／协议、加载优先级改变、本地适配冲突、Lua 错误或不通过的效果用例均阻止激活，说明适配需求 |
| 展开期间更新 | 当前会话始终使用原组合；结束并落盘后才生效。覆盖切换与新展开竞争、存活原生编辑器和文件占用 |
| 安装中断 | 分别在下载、提取、中间补丁、候选就绪、指针提交前后、生效确认前注入退出／终止；重启仅加载完整旧代或完整新代 |
| 生效后失败／手动恢复 | 从壳和设置入口均能恢复支持的前代；保留全部新旧用户数据、失败原因与候选 |
| 资源先更新再升级工具箱 | 旧随包资源不覆盖外部更新；最终组合和数据符合目标清单 |
| 工具箱先升级再更新资源 | 与上一行最终组合、文件树、有效配置和数据一致；无可兼容目标时保持原可用组合 |
| 历史与重试 | 旧文本、原事件、原报告、正式方案内容不变；新日志带组合版本；只更改脚本而不改 EXE 也能阻止不匹配的精确重试 |
| 关闭自动功能／离线 | 关闭后不自动请求、下载或提交；手动入口可用，已安装版本离线可训练和读历史 |

验收不能停在进程启动：必须检查真实召唤、抽卡效果、费用、灰流丽等响应与无效、连锁结果、区域／素材状态和报告归属；增加该次更新的代表性新卡及修改卡。普通战斗摘要过滤、完整原始证据、双方起手、先后手、LP、计时、AI 设置、方案保存与删除恢复都要回归。

后台桌面验收检查子窗口父子关系、缩放、可见帧、命中归属和没有合成层遮挡，并完成保存、关闭、重启、再读数据。新资源是否生效同时核对服务和原生端的组合 ID、候选特有卡号／文本／图片和规则结果。测试固定种子仅限隔离验收实例，正常训练保持随机。

相关变更实施时运行 `npm test`，相应静态检查、原生构建、`npm run test:desktop`、`npm run build:dir`、`npm run test:packaged`，最终发布包再校验内容与构建来源。所有图像和输入来自本应用后台渲染器／内部引擎接口，不移动系统鼠标、不发送全局按键。

仍需核实或确定：

1. 0901 包的精确最低前置版本、删除／重命名规则，以及未来上游是否提供安装脚本源码或结构化说明。列表顺序和安装器检测到 EXE 都不能代替这些证据。

6. 首版真实效果用例覆盖范围、资源代保留数量和磁盘预算。需要精确复现多久以前的尝试，会直接影响历史资源保存成本。
