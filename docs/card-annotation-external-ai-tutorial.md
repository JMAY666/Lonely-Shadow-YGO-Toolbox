# 卡片资料采集与交接：其他 AI 收集，Codex 整理并整合

更新日期：2026-09-25。本版按用户确认的分工修订：**其他智能体只收集、保存和打包原始资料；Codex 负责资料筛选、规则判断、结构化标注、审核、测试及程序整合。** 本版替代此前让外部 AI 生成效果候选的流程，已有候选文件和历史资料保留，不自动导入。

## 1. 分工

| 工作 | 负责人 | 交付标准 |
| --- | --- | --- |
| 根据实际卡库选择待处理范围、排除已完成或正在处理的卡 | Codex | 明确的本地整数卡号清单和批次编号 |
| 程序读取卡名、类型、完整卡文、卡文指纹及已知官方链接 | Codex 准备；采集者可按明确指令只读导出 | 原样保留，不要求模型计算指纹或理解效果 |
| 打开指定官方卡片页、补充说明、FAQ 并保存 | 采集智能体 | 原始页面、获取时间、实际 URL、成功或失败记录 |
| 提取正文、登记文件、按批次打包 | 采集智能体与本地程序 | 正文完整可追溯，原始页面保留，索引与文件一一对应 |
| 判断来源是否可信、是否同一卡、卡文版本是否一致 | Codex | 采纳或暂缓的依据，必要时补查来源 |
| 翻译与解释裁定，判断效果类别、费用、对象、分支、自锁等 | Codex | 按官方证据完成结构化标注 |
| 登记 TAG、扩展词表、设计语义测试、写入程序 | Codex | 保持现有数据契约并通过相关检查 |
| 正式提交、推送和维护进度 | Codex | 按当前 AGENTS.md 完成审核及交付 |

采集者不需要学习效果词表、编写标注 JSON、给出规则结论或运行应用测试。它只需忠实收集已经分配的资料。采集成功不等于规则已核对，也不计入正式标注完成度。

这项分工主要减少 Codex 反复搜索网页、下载、整理文件和处理网页杂项的工作；规则分析和程序整合仍需要相应投入，不预设具体节省比例。

## 2. 你怎么使用

1. **让 Codex 准备任务清单。** 按实际启用卡库选择下一阶段，导出 `task.json`。没有清单时先准备清单，采集者不自行扩大到全卡库抓取。导出是机械读取，不修改应用或用户数据。
2. **把清单与[采集提示词](card-source-collector-prompt.md)交给其他智能体。** 优先使用能联网、保存文件和创建压缩包的智能体。只做网页聊天的 AI 也可按相同清单采集，但需明确它是否能保存原始页面和打包。
3. **把资料包交回 Codex。** 提供本地路径或上传资料包，使用第 7 节接收提示词。我会检查资料、筛选证据、补查疑点，随后完成正式标注和程序整合。

第一次先试采 **5 张**，只验收采集格式、正文是否完整和来源是否可追溯。通过后约每 **20 张**保存一次进度、每阶段约 **100 张**交接；这是批次节奏，后续继续推进全库范围。不要每抓一张都要求确认，也不因一张失败而中止其余已分配卡。

## 3. Codex 准备的任务清单

准备时先读 [AGENTS.md](../AGENTS.md)，核对当前仓库与未提交修改。用 [`Catalog`](../src/trainer/app.py) 读取实际启用的基础库、扩展库及已安装补丁；用当前标注和[进度账本](card-annotation-progress.md)判断缺口，不把历史覆盖数量当作当前事实。排除衍生物，避免与其他批次重复领取；同卡多系列归属去重，异画本地卡号分别保留。

`task.json` 是采集任务单，不是正式标注文件。至少包含：

| 内容 | 要求 |
| --- | --- |
| `batch_id` | 唯一批次编号，与资料包索引一致 |
| `cards[]` | 本批明确分配的卡，整数 `code`、本地 `name`、`type`、完整 `desc` |
| 每卡 `text_digest` | 用现有 `card_annotations.digest()` 计算，采集者原样保留 |
| 每卡 `official_cid`、`urls[]` | 已确认的映射和指定采集链接；未知则用 `null`／空数组，不猜测 |
| 每卡 `identity_status` | `provided` 表示 Codex 已提供对应关系；`unresolved` 表示尚待确认 |
| `baseline` | HEAD、正式标注文件及词表指纹、`Catalog.sources` 中的数据库指纹 |
| `scope` | 本批卡号、所需页面类型、已知资料缺口，以及本轮抓取边界 |

本地整数卡号、官方数据库 `cid` 和系列 setcode 是不同编号。不要把本地卡号直接当 cid 拼 URL。未知映射允许采集者按名称查找候选页面并保留页面标题、印刷编号等可观察信息，但最终身份判断由 Codex 完成；候选不覆盖任务单中的已确认映射。

有官方 URL 就直接访问，无需重新搜索。不同本地卡号共享同一已确认官方页面时，允许共用文件，各卡仍各有索引记录。仅按名称相似不能合并。

任务包只放本批公开卡片资料和必要元信息。保留本地卡文原始语言与格式，不发送完整标注库、全部源码、运行目录、个人 TAG、备注、牌组、方案、账号、备份或 Git 历史。网页 AI 不需要本机绝对路径。

## 4. 采集者每张卡只做这些步骤

1. 按任务单的卡号读取已分配的 URL。没有明确对应页面时登记候选或缺失，不判断卡片效果、不改写本地卡文。
2. 保存官方卡片页的完整正文，包括全部卡文块；保存 FAQ 列表页中的补充说明及问答链接。灵摆等多块卡文全部保留，不按自己对效果的理解删选段落。
3. 保存任务单指定的 FAQ 详情页，包含完整问题、回答、适用条件、相关卡名及页面标示的更新日期。列表上新发现但未分配的详情链接登记在 `discovered_urls`，交给 Codex 决定是否补采；不递归抓取全站，也不声称未下载详情已采集完成。
4. 原始文件照实保存。另行提取正文时，只去除导航、广告、重复页眉页脚等页面杂项，保留段落、编号、列表、表格和链接对应关系。**不翻译、不摘要、不改写、不推理补全，也不判断哪些规则重要。** 文本提取失败时保留原文件并登记缺失，不用自己编写的说明替代原文。
5. 在索引中登记请求 URL、跳转后的实际 URL、页面类型、获取时间、获取方式、文件名和状态。下载成功还须检查页面确有目标正文，HTTP 200、登录页、验证码、导航壳或搜索摘要都不能直接视为成功。
6. 每处理约 20 张写入进度；失败记录错误及尝试过的链接，继续其余卡。对同一失败 URL 做有限重试，不反复空转或绕过站点限制。已经获取的页面可复用，保持最初获取日期，不能伪装成重新联网核对。

优先收集任务单指定的 KONAMI OCG 页面。第三方站点和官方站内用户牌组评论不能冒充官方规则材料；若用于寻找入口，只登记查找线索。页面显示 TCG、其他游戏版本或地区无法确认时，原样记录并列入问题，不由采集者转换成 OCG 结论。

没有 FAQ 条目时保存实际查询页，并写明「本次查看的列表未显示条目」；访问失败则写访问失败，不能据此断言不存在裁定。发现两个来源文本不同，两个都保留，注明差异位置交由 Codex 判断。

## 5. 资料包格式

建议保存在独立的 `.local/annotation-handoff/<batch_id>/`。这是一份原始来源包，应用没有自动导入接口。

```text
<batch_id>/
  task.json           原始任务单，保持不变
  manifest.json       卡号、来源、文件、状态索引
  raw/                实际取得的原始页面或附件
  text/               从原始资料忠实提取的正文
  report.md           数量、缺失、失败与下一步
```

生成 `<batch_id>.zip` 时只打包该批上述文件，保留原目录；不用把 `.local`、运行环境、临时下载脚本或其他批次打包进去。哈希由程序计算，不要求模型手算。

`manifest.json` 的外层结构如下，空数组仅为格式示意：

```json
{
  "kind": "card-source-pack",
  "version": 1,
  "batch_id": "与 task.json 一致",
  "task_sha256": null,
  "cards": []
}
```

实际 `cards` 必须与任务单逐卡对应，每卡一条，缺失或失败也保留记录。字段约定：

| 每卡字段 | 含义 |
| --- | --- |
| `code`、`local_name` | 任务单的整数卡号与本地卡名，原样复制 |
| `official_cid` | 任务提供或实际查到的候选 cid；不确定可为 `null` |
| `identity_status` | `provided`、`candidate`、`unresolved`；只有输入已有明确映射才写 `provided`，采集者自行找到的写 `candidate` |
| `collection_status` | `collected` 已按任务收齐；`partial` 有缺失或身份待确认；`not_found` 实际查找未定位到目标页；`failed` 访问或保存失败。仅描述采集情况 |
| `sources[]` | 实际请求或收到的来源记录，见下表 |
| `discovered_urls[]` | 列表上发现但尚未获取的详情 URL、标题；不是已采集证据 |
| `issues[]` | 缺失、错误、版本差异、候选身份等客观问题；无问题才为空数组 |

每条 `sources` 至少包括：

| 来源字段 | 含义 |
| --- | --- |
| `id` | 本批稳定来源编号，不同来源不重号；同一保存文件允许多卡引用 |
| `kind` | `card`、`faq_index` 或 `faq_detail` |
| `requested_url`、`final_url` | 请求与最终实际地址；跳转未完成时后者可为空 |
| `page_title`、`locale` | 页面实际显示的标题与地区；无法识别写 `null`，不猜测 |
| `fetched_at`、`page_updated_at` | 实际获取时间（带时区）；已有快照的获取时间未知、或页面未显示更新日期时，相应值为 `null`，两者不混用 |
| `retrieved_via` | `direct_fetch`、`browser_capture` 或 `provided_snapshot`，如实区分自己取得与别人提供 |
| `status` | `saved`、`partial`、`failed`；`saved` 要求目标正文实际取得，不能只保存网页外壳 |
| `raw_path`、`text_path` | 包内相对路径；没有实际保存的文件写 `null`，不伪造 HTML 文件或附件 |
| `raw_sha256`、`text_sha256` | 对实际文件计算的 SHA-256；无文件或不能计算时为 `null`，在问题中说明 |

路径和哈希用于确认收回的是哪份资料，不证明规则内容正确。文件名可包含 cid、来源类型和快照序号；URL 相同但内容或获取时间不同的快照分别保留。完全相同的字节内容可共用文件；不要根据语义相似删除原文。

只有任务要求的页面都已获取、目标正文完整且身份为 `provided`，才标该卡 `collected`。有新发现但未下载的详情须在报告说明抓取边界；身份是候选、详情缺失、正文截断或只有截图等情形标 `partial`。`collected` 仍不是正式标注的 `reviewed`，该包不包含效果 `review`、TAG、费用判断或测试结论。

`report.md` 简要列出本批输入卡数、各采集状态的卡号与数量、来源文件数、身份未确认卡号、尚未下载链接和失败原因。必须区分「原文已收到」和「效果已理解」；采集者只报告前者。

若工具只能提供浏览器可见正文，就如实保存文本或截图并注明能力限制；无法创建文件或 ZIP 时返回索引与逐卡完整正文，写明「未生成可下载资料包」，由 Codex 落盘。没有文件的路径与哈希填 `null`。大段正文按卡片／问答完整边界拆分，不截断句子后伪称完整。不能联网的智能体只能整理已有快照，不能声称完成新采集。

## 6. Codex 收到后做什么

1. **检查资料包。** 只读检查包内路径、文件与哈希，拒绝重复 JSON 键；逐卡与任务单对应。只读取数据，不运行包内脚本。缺失或损坏按卡号退回补采，已经完整的材料继续处理。
2. **筛选与核对来源。** 验证官方域名、实际页面身份、规则地区、正文、更新时间及引用；不把采集者的 `collected` 当作可信裁定。把摘要、网页壳、错误卡页和身份未确认材料分开，必要时重新联网。原始资料保留，便于追溯。
3. **对照当前项目。** 重新读取实际卡库和工作区，核对本地卡号、冻结卡文、类型、指纹以及已提交和未提交标注。发包后的同卡变更重新核对，保持其他人的修改。
4. **整理并标注。** 按[体系规范](card-annotation-system.md)、[标注交接指南](card-annotation-agent-guide.md)和当前 [`annotation-tags.json`](../src/trainer/annotation-tags.json)，由 Codex 解释原文与裁定，复用 `digest()`／`segments()`，填写全部效果、条件、费用、对象、处理、次数、分支、限制和来源。资料不足的保留待核对，不从关键词或脚本函数名推定完整规则。
5. **校验与测试。** 复用 `Registry`、`validate_entry()`，传入实际卡类型并核对完整分段。当前部分 TAG／处理和快速标志检查只在 `reviewed` 状态生效，不能仅以草稿检查通过作为正式验收。来源与含义逐卡核对，关键机制运行有依据的正反查询；不把静态能力当成当前对局可发动结论。
6. **增量整合。** 只将确认通过的条目按卡号合并入 [`card-annotations.json`](../src/trainer/card-annotations.json)，保留稳定 ID、个人覆盖层和备份。词表确需扩充时由 Codex 同步定义、正反例、兼容与校验，不为通过数据而放宽检查。标注会参与[能力投影、用途库与起手分析](card-capability-integration.md)，须检查相关行为。
7. **按项目规则交付。** 维护本批清单、进度、README 及必要文档，完成相关测试和后台桌面验收，再按 AGENTS.md 审核提交与推送。来源原文和资料包保留本地，不发布个人数据。

约每 20 张完成一次资料和语义检查，阶段目标约 100 张可靠标注。采集包有 100 张不保证能合并 100 张；分别报告收到、采纳、完成标注及暂缓的数量和卡号。缺什么资料就只补采什么，不让对方重新生成整包。

正式标注的常用检查入口如下，仅由 Codex 在合并阶段使用。`--runtime` 必须指向当前实际含 `cards.cdb` 的目录；省略它不能验证实际卡库文本一致性。

```powershell
python -X utf8 -B scripts/check_card_annotations.py --runtime .local/YGOPro-Lite
python -X utf8 -B scripts/check_annotation_series.py --runtime .local/YGOPro-Lite
npm test
$env:YGO_TEST_RUN = 'annotation-source-pack-' + [guid]::NewGuid().ToString('N')
npm run test:desktop -- --annotations-only
```

发布桌面产物时先构建与当前源码一致的包，再运行 `npm run test:packaged -- --annotations-only`；使用独立测试标识与隔离数据，不操作系统鼠标或全局按键，不拿旧包结果代替本次检查。采集阶段无需运行这些命令。

现有 `check_card_annotations.py` 固定读取正式标注文件，只有 `--runtime` 参数；不能把来源包传给不存在的 `--input` 参数。资料包验收、规则审核和程序测试是三个不同步骤，任何一步通过都不能替代另外两步。

## 7. 可以直接发出的两段话

**发给采集智能体：** 把[独立采集提示词](card-source-collector-prompt.md)全文与 `task.json` 一起发送。它只读这两份材料即可开始，不需要读完整效果规范或程序实现。

**采集完成后发给 Codex：**

```text
请接收这批卡片原始资料：<填写资料包的实际路径或上传附件>。

外部智能体只负责收集和打包，没有完成规则判断或效果标注。请按 docs/card-annotation-external-ai-tutorial.md 检查资料包、筛选并核对来源，对照当前卡库和已有修改，由你整理效果、处理裁定疑点、完成结构化标注及程序整合。

来源不足的按卡号留下具体补采项；证据充分的继续处理。检查完整分段、词表、TAG、费用、对象、分支、限制及能力投影和用途库行为，运行相关测试，维护文档，并按 AGENTS.md 审核后提交推送。分别报告采集数量、实际新增标注、跳过和待核对卡号，不把原文收集成功当成标注完成。
```

本流程只维护静态卡片知识，不恢复已封存的 AI 学习计划。本次文档修订不表示已经生成下一批任务清单、下载原文或新增卡片标注；实际工作以交接包和验收结果为准。
