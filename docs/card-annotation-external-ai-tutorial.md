# 把卡片功能标注交给其他 AI：操作教程与可复制提示词

编写日期：2026-09-25。按当前仓库的标注格式与 1.49.0 能力接入方式整理；执行时以当前代码、词表、实际卡库及 `AGENTS.md` 为准。本教程不固定已完成数量，也不重新执行历史补卡清单。

目标是让其他 AI 承担逐卡查资料、拆解效果、填写结构和返修的主要工作。本地程序负责读取卡库、计算指纹、分段、检查格式和统计；审核者负责核对证据及合并。审核者也可以是有相应能力的其他智能体，不要求每批都交回 GPT。

## 1. 你实际需要怎么操作

| 对方的能力 | 发什么 | 怎么接回结果 |
| --- | --- | --- |
| 能读取本机项目、联网、运行命令的编程智能体 | 本教程路径，再复制第 7 节提示词 A | 它先准备批次并产生候选；完成后发提示词 C，让它或另一个智能体验收合并 |
| 只能使用网页聊天，但能联网、收发文本附件 | 先让本地智能体按提示词 A 的「仅准备资料包」模式导出，再上传本教程和精简资料包，发送提示词 B | 下载返回的 JSON 与问题清单，交给本地智能体执行提示词 C |
| 不能联网的 AI | 与上一行相同，但资料包必须含已经获取的官方卡文、补充说明和相关 FAQ | 只能依据给定资料生成候选；证据缺口留待核对，不能声称自己联网验证过 |

首次换模型，先用 **5 张卡试做**，选择本批中不同机制的卡；验收后再扩大到每小批约 **20 张**，每阶段约 **100 张**。5 张和 20 张是质量检查点，不是全库目标的缩减。后续继续按当前未覆盖系列推进；复杂卡可以拆成更小批，来源不足的卡单列并继续其他卡。

建议保留两个对话：一个做资料与候选，一个做审核。开始新批次只补充该批输入、未解决问题和必要规范，不重复粘贴完整项目、全部标注或所有历史对话。先比较试做的正确率与返修量，再决定是否继续使用该 AI；本教程不承诺某个模型的价格或节省比例。

> 最短启动方式：把本文交给能操作项目的智能体，发送「请按本文第 7 节提示词 A 执行，工作目录为 `E:\AI项目\游戏王工具箱`。先试做 5 张，通过审核后按每批约 20 张、每阶段约 100 张持续推进。」

## 3. 本地智能体准备精简资料包

这一步使用程序处理机械工作。允许临时脚本放在本批独立的 `.local/annotation-handoff/<batch_id>/`，不要为导出资料改写应用源码。`batch_id` 使用日期、批序和随机后缀，避免覆盖另一批。

1. 检查仓库根目录、分支、HEAD、远程、工作区和暂存区。记录正在修改的文件及卡号；已有未提交的新增卡也视为占用，不分给另一位标注者。若无法确认占用范围，跳过这些卡，先做其他未覆盖卡。
2. 使用真实 runtime 的 `Catalog`，按当前卡库排除衍生物，区分已完成、已有草稿、过期、部分和未覆盖。优先选择尚未处理的完整系列；多系列归属去重，异画本地卡号分别保留。没有系列归属的卡后续另排队，不能永久遗漏。
3. 保存本阶段约 100 张候选及分批卡号。每批约 20 张；首次试做只发 5 张，后续不能把这 5 张再次计为新增。先保存阶段清单，再逐个发小批。
4. 对本批每张卡读取整数卡号、`name/type/desc`、系列归属；用项目 `digest(desc)` 生成指纹，用 `segments(desc, type)` 生成完整分段。完整卡文与分段键由程序复制，不能要求聊天模型自己算 SHA-256 或猜效果编号。
5. 从正式资料提取 2—4 个与本批机制相近的完整例子，包含一个容易混淆的反例说明；不要把整个 `card-annotations.json` 塞进资料包。例子用于格式参考，其裁定不可自动套用到新卡。
6. 导出当前词表，并附体系规范中涉及本批的定义与正反例。历史指南中的取值列表可能落后，以当前词表为准。对方需联网时，给它已核对的官方链接；没有可靠 cid 映射时明确待查，不能把本地卡号直接拼成 cid。
7. 保存批次基线：HEAD、正式标注文件与词表的 SHA-256、`Catalog.sources` 中的数据库指纹、本批已有条目内容，以及 `digest/segments/validate_entry` 所在文件版本。发包后发生变化时，接回结果必须重新核对。

建议交付以下文件。这里的文件名是本教程约定的**交接格式**，不是应用已有的导入接口：

| 文件 | 内容 |
| --- | --- |
| `task.json` | `batch_id`、基线版本与指纹、当前批次卡号及每卡 `code/name/type/desc/text_digest/segments`；阶段范围和完成口径 |
| `vocabulary.json` | 从当前 `annotation-tags.json` 导出的完整词表，不自行改名或删去定义 |
| `examples.json` | 2—4 个正式条目；与本批输出分开，不计为待做卡 |
| `rules.md` | 本批必需的规范摘录、易错点和官方资料索引；不足时补读原规范 |
| `sources/` | 需要离线交接时附官方资料正文及 URL、获取日期、地区和来源定位；联网工作者可自行获取 |

来源原始 HTML 保留在本地 `sources/`，输入模型时尽量提供卡文、补充说明和相关 FAQ 正文，去除导航与用户牌组评论。不得把关键条件删掉来节约 token。证据记录至少能定位到 URL、卡片 cid、获取日期和具体效果；卡文与 FAQ 版本矛盾时列出差异，不自行选一个凑完成。

只分享本批公开卡片资料、规范和脱敏元信息；不打包整个 `.local/`、运行目录、Git 历史、个人 TAG、备注、牌组、方案、账号或备份。路径等本机元信息留在本地清单，发给网页 AI 的清单使用相对文件名。

## 4. 每张卡的工作顺序与质量标准

1. **认准卡片。** 本地整数卡号是身份；官方 `cid` 是网页编号；系列 setcode 是系列身份。卡名仅用于核对。异画卡可以共用同一官方证据，但须先核对同名、类型和完整卡文，不合并本地卡号。
2. **核对官方 OCG 来源。** 打开卡片页、补充说明以及涉及疑点的 FAQ；URL 存在或搜索摘要出现卡名不等于读过来源。区分 OCG 与 TCG。找不到证据时保留疑点，不让 AI 的记忆代替核对。
3. **逐段填写。** 保留 `m-pre`、无编号段、全部编号段和灵摆 `p*`／怪兽 `m*` 双区。无编号文字可能是效果、素材手续、次数限制或描述，必须判断；缺标签不等于无效果。
4. **拆开六类内容。** 发动条件和区域、费用、对象、处理、次数、限制分别填写。处理保留数量、来源与去向、执行者和受影响者、顺序、分支、可选项、持续时间及自锁开始时点。
5. **再填写 TAG。** TAG 反映已经写明的能力；不能从费用、响应条件、卡文提到的其他卡推导本卡有某能力。处理中的分支与后续也要核对标签，但互斥分支不表示可以同时执行。
6. **留下可追溯依据。** 每卡 `sources[]` 保存来源；逐效果备注用 `source_refs` 指向本卡实际存在的来源 id。疑点要具体到卡号、效果键、问题和缺少的证据。

关键边界速查：

| 容易做错的地方 | 要求 |
| --- | --- |
| 丢弃／送墓费用与效果送墓 | 按实际费用条件分别记录；不能把费用标成效果能力 |
| 检索、回收、回手与抽卡 | 用现有动作与 TAG，明确来源区域；抽卡不能写成检索 |
| 取对象与结算时选择 | 前者进入 `targeting`，后者在处理选择器描述，不凭「选择」一词猜测 |
| 发动无效与效果无效 | 分开记录；破坏是另外的处理 |
| 诱发与诱发即时 | 能在对方回合触发，不足以把 `fast_effect` 设为 `true` |
| 魔法卡发动与魔法效果发动 | 从区域和官方分类判断，不用一个类别笼统代替 |
| 素材手续与发动费用 | 素材要求、非效果召唤手续、结算中的素材处理分开 |
| 使用次数、发动次数、共享次数 | 保留原文限制关系，不能按旧字段英文名字猜含义 |
| 自锁与对方封锁 | 说明适用者、开始／结束时点、是否追溯此前行动 |
| 顺序与互斥分支 | 用 `then`／`branches` 保留关系，不压成平行能力清单 |
| 模糊区域 | 仅知「场上」不能声称已证明每个特定子区域都可选 |

例如，当送墓会被除外替代时，需要把卡**送去墓地作为费用**的效果不能支付该费用来发动；不能笼统写成「费用仍可照常支付」。依据：[KONAMI OCG FAQ 14540](https://www.db.yugioh-card.com/yugiohdb/faq_search.action?ope=5&fid=14540&request_locale=ja)，2026-09-25 复核。本例只说明为什么必须区分费用和处理，不替代本批逐卡核对。

正式字段形状以当前条目和校验器为准，特别注意：

- `review.status` 只使用 `draft`／`reviewed`，`review.origin` 使用项目允许值。`pending` 等界面状态不能直接填入这里。
- 外部工作者统一交付 `draft/auto`；这里表示候选尚未由接收方审核，不评价模型能力。只有完成资料核对与验收后，审核方才按现有人工资料核对流程写成 `reviewed/manual`。不得伪称真人审核或填写未执行的引擎验证。
- `review.checked_on` 是合法的 `YYYY-MM-DD` 日期；候选中填写实际整理日期，并在 `basis` 明示待审核。`sources[].checked_on` 保留该来源实际核对日期，不能把继承的旧资料伪装为今天重新联网取得。
- `structure.usage` 是受控字符串数组；`cost`、`targeting`、`processing` 是对象数组；`branches` 内使用 `actions`，不能写成任意自然语言键名。
- `targeting[].count` 当前要求非负整数；`processing[].count` 只使用当前校验器接受的形式。不能表示某个细节时提出词表／结构问题，不能偷偷扩展格式或曲解数量。
- 新词表需求放进提案，说明定义、正例、反例和旧数据兼容；工作者不改校验器来让自己的输出通过。
- 来源不足时，不把未知写成 `false`、`[]` 或 `no_effect=true` 来假装确定。无法提供符合格式的条目就列入 `unresolved`，不伪造来源。

## 5. 对方应返回什么

每批返回 `candidate.json` 和简短的 `report.md`。候选文件的最外层如下；这是空壳示意，实际 `cards` 必须填完整条目，不是要求交付空对象：

```json
{
  "batch_id": "与 task.json 一致",
  "cards": {},
  "unresolved": [],
  "vocabulary_proposals": [],
  "test_cases": []
}
```

- `cards`：键为本地卡号的十进制字符串，值沿用正式条目结构，`code` 为整数。只返回本批新增／待修候选，不复制整库。保持输入的 `frozen_text`、`text_digest` 和分段身份。
- `unresolved`：每项包含 `code`、`effect_key`（整卡问题可为 `null`）、`issue`、`needed_evidence`；有草稿的卡也可以在此列出疑点。每个输入卡号必须有候选或明确的未解决说明，不能无声漏卡。
- `vocabulary_proposals`：每项包含词表名称、建议取值、定义、正反例和所需兼容处理；只是提案，不表示已经登记。
- `test_cases`：关键机制的正反查询，包含卡号、查询条件、预期效果键及依据；仅生成用例不能声称已经执行。费用／处理、无效类型、区域差异、分支等优先覆盖。
- `report.md`：本批卡号、证据情况、完成的操作、未执行的检查、未解决项和下一批起点。不要输出长篇思考过程，也不要声称「全部正确」。

聊天输出太长时，按完整卡片边界拆成多个合法 JSON 文件，每份使用相同 `batch_id`，卡号不得重复。不要在字符串或一个效果对象中间截断；不能交付被截断的 JSON 后声称已完成。

工作者可先在 5 张试做中校验输出形状；格式错误先局部返修，避免一次生成 100 张后整批返工。续接对话只传失败卡、错误信息、对应规范和必须的上下文；不让已通过卡重复生成。

## 6. 本地审核与合并

候选生产和正式合并是两个阶段。候选保存在独立 `.local/annotation-handoff/<batch_id>/`，不进入生产标注文件；正式合并后才执行项目的提交与推送流程。应用目前没有本教程交接包的自动导入功能，不能把 `candidate.json` 放进目录后宣称已生效，也不能用界面的「个人修正」代替完整结构导入。

### 合并前的必要检查

1. 解析 JSON 时拒绝重复键；检查批次身份、输入卡号、候选／问题清单是否逐卡对应、有无额外卡号。对照发包时的基线与当前工作区；全局文件指纹变化时检查具体影响，不直接覆盖。相同卡号或词表发生变化的候选重新核对，其他人的新增保持原样。
2. 从实际 `Catalog` 重新读卡文、类型与分段；逐卡比较冻结原文和指纹。不能仅更新指纹来掩盖文本变化，不能把 `no_effect` 当作绕过分段检查的开关。
3. 复用 `Registry` 和 `validate_entry(entry, registry, segment_keys, card_type=...)` 检查候选。全段完整性另行检查：当前分段键与效果键是否一致；明确无效果卡按官方文本和当前规范单独核对，保留必要素材／规则段。
4. **草稿校验不等于正式校验。** 当前 `validate_entry()` 的部分 TAG／处理、效果类别／快速标志检查只对 `reviewed` 生效。对拟接纳条目的内存副本临时使用 `reviewed/manual` 并传入实际卡类型，再执行校验；这只是检查调用，不写回候选、不宣称已经审核。此步骤也不能替代来源和含义核对。
5. 逐卡核对官方来源身份、规则地区、日期、正文及备注引用。存在疑点、来源冲突、复杂分支、次数共享、复制效果、新词表的卡必须重点复核。抽样只能用于评估模型是否适合继续，不能代替其余卡成为 `reviewed/manual` 所需的逐卡核对。
6. 使用隔离数据执行关键机制的查询正反例；新测试须针对可能出错的行为，不只检查数量或复述输入。旧 `check_annotation_batch4.py` 等脚本针对各自历史卡号，跑过它们不能证明新批语义正确。
7. 只把证据充分、格式与含义均核对通过的卡合并进正式资料。疑点留在本批候选和问题清单；不要为凑 100 张把它们标成完成。合并前重读最新文件，按卡号增量合并，不整库覆盖、不重排无关条目、不更改既有稳定 ID。

`scripts/check_card_annotations.py` 当前只有 `--runtime` 参数，固定读取正式标注文件；**没有 `--input`、`--file` 或交接包导入参数**。候选阶段用上述 Python 函数做内存检查，合并后才用此脚本验收正式数据。它检查结构、词表、来源字段、卡文与覆盖，不能判断网页是否真的支持标注结论。

### 合并后的命令与验收

以下在项目根目录执行；`.local/YGOPro-Lite` 是本机示例，使用当前确实包含 `cards.cdb` 的有效运行目录。只读检查可以读卡库，不启动用户正常配置下的应用，也不执行用途库迁移的 `--apply`。

```powershell
python -X utf8 -B scripts/check_card_annotations.py --runtime .local/YGOPro-Lite
python -X utf8 -B scripts/check_annotation_series.py --runtime .local/YGOPro-Lite
python -X utf8 -B -m unittest discover -s tests -p 'test_card_annotations.py' -q
python -X utf8 -B -m unittest discover -s tests -p 'test_card_capabilities.py' -q
python -X utf8 -B -m unittest discover -s tests -p 'test_annotation_knowledge.py' -q
node --test tests/card_annotations_view.test.cjs tests/card_capabilities.test.cjs
```

约每 20 张检查一次来源、分段、机制正反例和实际 runtime 标注校验，通过后继续下一批。系列展示校验和效果标注是不同口径，不能互相代替。阶段正式交付时按项目规范执行完整检查与后台桌面验收：

```powershell
npm test
$env:YGO_TEST_RUN = 'annotation-handoff-' + [guid]::NewGuid().ToString('N')
npm run test:desktop -- --annotations-only
```

发布桌面产物时，先构建当前源码对应的包，再验收该包：

```powershell
npm run build:dir
$env:YGO_TEST_RUN = 'annotation-handoff-packaged-' + [guid]::NewGuid().ToString('N')
npm run test:packaged -- --annotations-only
```
